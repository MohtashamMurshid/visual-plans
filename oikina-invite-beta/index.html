The invite itself proves eligibility. Issue a random, expiring CLI credential and show it once. Add account passwords or passwordless sign-in only when Oikina ships a user-facing dashboard that needs repeat browser sessions.

Product decisions.

Minimal, but not shared-secret minimal

Identity

Name only

Store a display name for support and audit records. Internal tenant and principal IDs stay random and non-guessable.

Credential

API key, shown once

Use the existing oikina_… shape, scrypt hashing, mandatory expiry, revocation, and last-used metadata.

Isolation

One tenant per friend

Each credential can create and update only that tenant’s app slugs. No beta user shares Mohtasham’s operator token.

The beta-user journey.

Under two minutes

01Receive link

02Enter name

No email, ID, or password required for this small controlled beta.

Architecture.

Keep public enrollment away from deployment authority

Public surface

Invite redemption page

Captures the token from the URL fragment, clears it immediately, accepts a bounded display name, and disables caching.

→
Private authority

Control-plane API

Consumes the invite transactionally, creates tenant + principal, hashes the deploy key, records audit metadata, and later authorizes deploy targets.

→
Existing data plane

Hosted Runtime

Asks the private control API whether this key owns the requested slug, then keeps the filesystem registry as deployment activation authority.

Important current-state constraint: Oikina’s PostgreSQL control-plane package already models principals and secure deploy credentials, but current main documents it as separate from the live filesystem-backed Hosted Runtime. This beta must therefore include an explicit, tested authorization cutover—not just a signup form.

Implementation roadmap.

TDD · feature → staging → main

01
Schema

Model invites and tenant ownership

Add one-use invite records and make deployment ownership unambiguous.

  • Store invite prefix + scrypt hash, expiry, creator, consumed/revoked timestamps.
  • Create one organization and principal per accepted friend.
  • Make deploy-token prefixes discoverable globally without storing raw keys.
  • Enforce global app slug ownership before the live cutover.
Migration tests + disposable PostgreSQL integration
02
Domain service

Redeem exactly once

One transaction turns an unused invite into a tenant, principal, and credential.

  • Reject expired, revoked, malformed, replayed, or concurrent redemption.
  • Bound and normalize display names without deriving public slugs from them.
  • Return the raw deploy key once; audit only safe IDs and public prefixes.
Race test: 20 redeemers → exactly 1 success
03
Enrollment UI

Ship the one-link claim page

A tiny page in Console, not a new user dashboard.

  • Use /beta/redeem#<invite> so reverse-proxy logs do not capture the secret.
  • Clear the fragment before network requests; no third-party scripts or analytics.
  • Use no-store, Referrer-Policy: no-referrer, CSRF/origin checks, rate limits, and one-time key disclosure.
Browser E2E + back/refresh/BFCache leak checks
04
Private API

Authorize CLI deployments

Connect secure credential metadata to the filesystem-backed deploy path.

  • Run a private control-plane API; PostgreSQL remains private and never reaches browser code.
  • Hosted Runtime submits bearer credential + manifest slug over the private service channel.
  • First deploy claims an unused global slug; later deploys require the same tenant.
  • Fail closed on auth-service outage; retain owner token only as a documented break-glass credential.
Cross-tenant overwrite and slug-race tests
05
CLI + operations

Validate before saving

Make onboarding fail early and give Mohtasham basic beta controls.

  • oikina login calls a safe validation endpoint before writing credentials.
  • Add owner-only invite issue/list/revoke commands or script; no admin UI yet.
  • Default: invite 7 days, deploy key 30 days, manual reissue, immediate revoke.
  • Never print keys in logs, argv-based admin automation, telemetry, or audit JSON.
Packed CLI smoke + revoke/expiry checks
06
Rollout

Release to a tiny cohort

Start with two friends, then widen only after clean evidence.

  • Backup control-plane DB and filesystem registry; backfill and verify existing app ownership.
  • Canary new auth with feature flag, then remove broad beta access to the shared token.
  • Run real signup → login → deploy → redeploy → revoke E2E.
  • Track only aggregate success/failure and safe IDs; no raw invite or credential material.
2-user canary → 10-user beta after 48h

Security and product risks.

What can sink a “simple” invite flow

P1 · tenant escape

One friend overwrites another app

Mitigate with tenant-derived authorization, global slug claims, transactional first-deploy ownership, and adversarial cross-tenant tests.

P1 · secret leakage

Invite or API key lands in logs

Use URL fragments, no-referrer/no-store headers, one-time disclosure, secret-key audit guards, and log/telemetry regression scans.

P1 · split authority

PostgreSQL and filesystem disagree

Keep PostgreSQL as authorization/ownership metadata and the filesystem as activation authority; define compensating retry and fail-closed behavior.

P2 · support load

User loses the one-time key

Do not recover raw keys. Revoke and issue a replacement through the owner-only flow.

Explicitly not in beta v1.

Protect the small scope

No password accounts

  • No password hashing/reset emails.
  • No social login or SSO.
  • No persistent browser account session.

No user dashboard

  • No deployment list or release history UI.
  • No billing, teams, roles, or custom domains.
  • The CLI response is the deployment receipt.
