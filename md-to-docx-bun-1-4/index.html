How md-to-docx should—and should not—use Bun 1.4.

Add Bun as a supported, measured runtime without weakening Node/browser compatibility or replacing the package’s Markdown AST and secure image pipeline prematurely.

Decision snapshot.

The short answer

Adopt Bun 1.4 as an optional runtime and CI target—not as the package’s new foundation.

Bun 1.4 already installs the packed package, imports the library, and runs the CLI successfully. It also cut one local cold CLI sample by 38.1%. But the full native Bun test run exposed one abort-propagation mismatch in the remote-image path, while Node/Jest remains fully green. Keep Node as the compatibility baseline; promote Bun only after the security-sensitive suite is clean.

Interpret the benchmark narrowly.

The seven-run CLI sample proves a worthwhile optimization hypothesis, not a universal performance claim. Add representative small, large, image-heavy, reference-DOCX, and multi-section fixtures before publishing speed numbers.

Where Bun 1.4 benefits us.

Use the parts that fit the product

Runtime + CLIUse now

Offer documented bunx @mohtasham/md-to-docx and Bun library usage after CI proves the packed artifact. Faster Linux startup can matter for one-shot conversions and serverless jobs.

CI compatibilityUse now

Move the existing consumer lane from Bun 1.3.13 to 1.4.0 and add an explicit native-runtime lane. Bun’s larger Node-compatibility surface reduces friction, but our own tests remain the acceptance oracle.

Parallel testsAfter fix

bun test --parallel ran the suite quickly and merged worker output. Use it as fast feedback once 244/244 pass; keep canonical Jest on Node until parity is sustained.

Package hygieneEvaluate

bun audit fix, bun dedupe --check, and bun prune --production can simplify Bun-native apps. They should not create a second authoritative lockfile in this npm-published library without a deliberate package-manager policy.

Bun.ImageExperiment

Potential optional server-only adapter for decode/resize/transcode benchmarks. It may help image-heavy conversions, but must preserve image bytes, dimensions, accessibility metadata, limits, and browser builds.

Where Bun does not benefit us.

Avoid attractive rewrites with negative product value

Do not replace the Markdown parser.

  • Bun.markdown emits HTML, React, or callback-rendered output—not the mdast contract used by the converter.
  • The package relies on unified, remark-gfm, remark-math, plugin transforms, captions, cross-references, and custom renderers.
  • A Bun-only parser would break the Node/browser portability that is a core selling point.
  • Bun warns its HTML output is unsanitized; HTML is not our DOCX intermediate representation anyway.

Do not replace the secure fetch path.

  • Remote images use Node DNS/net plus an Undici Agent that pins the verified IP while preserving TLS server name.
  • This is deliberate SSRF/DNS-rebinding protection, not generic fetch() plumbing.
  • The only native Bun failure is in image-abort propagation; that path needs deeper runtime verification before production claims.
  • Bun.WebView, cron, FFI, and the Zig→Rust rewrite do not improve Markdown→DOCX conversion.

Implementation roadmap.

Four gated milestones

01

Declare Bun 1.4 support without changing the default runtime

Update .github/workflows/ci.yml from Bun 1.3.13 to an exact 1.4.0 pin. Keep Node 18/20, npm ci, Jest, lint, TypeScript, and the Next.js browser bundle as required checks. Add README install/CLI examples only after the packed consumer passes on CI.

npm run build · npm run test:package-manager -- bun

Low risk
02

Close native-runtime parity—especially abort and SSRF behavior

Add a Bun 1.4 native lane and reproduce the one failing image-abort test in isolation. Determine whether it is Bun’s Jest spy compatibility, worker isolation, or a real fetch/AbortSignal semantic difference. Add a runtime-neutral test seam only if needed; never weaken DNS pinning, HTTPS-only rules, redirect revalidation, byte limits, or caller cancellation.

bun test tests/processing-limits.test.ts · bun test --parallel=4 · gate: 244/244

Blocker
03

Build a representative Node vs Bun benchmark

Add deterministic fixtures for tiny CLI startup, large Markdown, syntax highlighting, data-URL images, reference-DOCX generation, and multi-section documents. Record warm/cold latency, peak RSS, output validity, and normalized OOXML equivalence. Run enough repetitions and publish medians—not a single marketing number.

Choose the supported tier from predeclared gates

Promote Bun to a documented first-class runtime only if package/CLI, browser bundling, all correctness tests, and security tests pass, with no output-contract regressions. Keep it Tier 2 if it is useful but needs exceptions. Reject deeper migration if gains are limited to installation/test tooling.

Go / no-go

Acceptance gates.

What “Bun supported” must mean

Correctness

  • 244/244 native tests pass.
  • Packed library import and CLI generate valid ZIP/DOCX.
  • Normalized OOXML matches expected semantics.
  • Reference-DOCX and browser bundle remain green.

Security

  • Abort propagation passes reliably.
  • Loopback/private IPs and DNS rebinding stay blocked.
  • Redirect, timeout, size, and image-count limits hold.
  • No replacement with unpinned generic fetch.

Maintenance

  • One authoritative dependency policy.
  • Exact Bun version in CI.
  • Node baseline remains release-blocking.
  • No duplicated parser/runtime code path.

Performance

  • Representative fixtures, not one sample.
  • Latency and RSS measured separately.
  • Output validity checked after every run.
  • Claims tied to OS, runtime, fixture, and commit.

Go / no-go rule.

Predeclare the decision

Go now: Bun 1.4 compatibility lane. No-go now: Bun-first rewrite.

Ship the low-risk support work if Bun 1.4 passes the existing packed-consumer check. Do not advertise first-class runtime parity until the native suite is fully green. Do not adopt Bun.markdown or Bun-only image primitives unless a separate benchmark proves material benefit without reducing Node/browser reach or security guarantees.
