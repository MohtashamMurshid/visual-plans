Decision snapshot.

Recommended first experiment

Use a fresh benchmark repo first; validate on your real repo second.

A controlled domain-realistic repo lets us pre-write hidden tests, reset identical baselines, and avoid production history leaking the intended implementation. It should still generate real .docx files and inspect their OOXML. After the pilot works, repeat two representative tasks against your existing Markdown→DOCX repository.

Why not one fake feature?

  • One task is dominated by luck and prompt interpretation.
  • A trivial toy rewards fast coding, not maintainability or regression control.
  • A single judge preference cannot establish which workflow is better.
  • Use several task shapes and compare paired outcomes.

What the pilot answers

  • Does enforced test-first improve hidden acceptance?
  • Does it reduce regressions and reviewer-found defects?
  • Are its generated tests better at detecting mutations?
  • Is any quality gain worth extra tokens and wall time?

The two arms.

Same task, budget, model and baseline

Arm T · test-first

RED → GREEN → REFACTOR

  1. Inspect repository and requirement.
  2. Add public tests only; implementation edits forbidden.
  3. Run tests and save evidence of the expected failure.
  4. Commit the test-only checkpoint.
  5. Implement the smallest complete fix.
  6. Run public suite, refactor, and submit.
Arm I · implementation-first

BUILD → TEST → REFACTOR

  1. Inspect repository and requirement.
  2. Implement first; test-file edits forbidden.
  3. Run existing checks and save the implementation checkpoint.
  4. Commit the implementation-only checkpoint.
  5. Add tests afterward.
  6. Run public suite, refactor, and submit.

Enforce the workflow mechanically.

The runner records file changes and commits at each phase. A session that edits forbidden paths, skips the red proof, reads hidden tests, or exceeds the shared budget is marked protocol-invalid—not quietly counted as a normal failure.

Benchmark task set.

Realistic, independently scorable

Pilot tasks 01–04

  • Nested ordered lists: preserve start values and indentation in OOXML.
  • Code blocks: language-aware style, whitespace preservation, no accidental paragraph splitting.
  • Tables: alignment, empty cells, escaping, and deterministic column widths.
  • Links: external hyperlinks, fragments, malformed URLs, and relationship deduplication.

Pilot tasks 05–08

  • Images: local assets, missing files, size limits, and descriptive errors.
  • Footnotes: repeated references, numbering, and OOXML relationships.
  • Metadata: title/author fields without nondeterministic output changes.
  • Regression repair: a seeded bug spanning parser, document model, and renderer.

Task construction rule.

Each task gets a visible specification, visible starter tests, a private acceptance suite, and several seeded edge cases. Hidden assertions must test observable DOCX/OOXML behavior—not require the evaluator author’s preferred internal architecture.

Scoring hierarchy.

Machines first, taste second

Hidden acceptance

Pass fraction across task-specific private tests plus the unchanged regression suite. A task is “solved” only if all critical acceptance cases pass.

Primary
Protocol validity

Correct phase ordering, genuine red failure for Arm T, no forbidden edits, no hidden-test access, and budget compliance.

Gate
Test strength

Mutation score on relevant code plus whether agent tests catch evaluator-seeded faults without overfitting implementation details.

Secondary
Efficiency

Tokens, estimated API cost, wall time, tool calls, retries, and accepted solutions per unit cost.

Secondary
Engineering quality

Blind rubric: correctness risks, clarity, scope discipline, API compatibility, maintainability, and test quality.

Judge

Blind judging.

Codex opinion is evidence, not ground truth

Codex judge sessions

  • Use fresh sessions that did not implement either candidate.
  • Rename candidates A/B and remove workflow/commit-message clues.
  • Give requirement, relevant diff, public test output, and rubric.
  • Run one packet as A/B and another as B/A to expose position bias.
  • Require per-criterion scores and cited file/line evidence.

Your human review

  • Review blind before seeing which arm produced each candidate.
  • Record scores before discussing results with any judge.
  • Flag whether you would merge it, request changes, or reject it.
  • Reveal the arm only after automated and qualitative scores lock.
  • Keep disagreements; do not force one synthetic consensus score.

External validity

Validity risks.

What could fool us

Judge circularity

  • Codex judging Codex may prefer its own style.
  • Mitigation: hidden behavior is primary; human review stays independent.

Workflow leakage

  • Tests, commit order, or comments may reveal the arm.
  • Mitigation: normalize packets and score judge position consistency.

Task contamination

  • Agents may know common public challenge solutions.
  • Mitigation: author original domain tasks and private edge cases.

Overclaiming

  • Eight tasks cannot prove universal agent behavior.
  • Mitigation: call it a pilot, publish paired outcomes, then scale tasks/models.

Go / no-go rule.

Declare before running

Prefer test-first only if it wins on accepted solutions—not aesthetics alone.

Adopt Agent TDD as the default if Arm T solves more paired tasks under hidden acceptance and does not impose an unacceptable cost/time penalty. If correctness ties, use mutation strength, regressions, and blind merge decisions as tie-breakers. If results split by task type, adopt a routing policy instead of declaring one universal winner.
